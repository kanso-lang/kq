# The CPU features glibc's ifunc resolvers read when they pick memcpy, memcmp,
# strlen and their neighbours, as ld.so reports them. Sorted, so a diff reads
# line by line. bench/instructions.sh consults this ONLY when a row has moved —
# it never refuses on its own, and the reasons are in that file's header.
#
# THIS IS A CPU ON WHICH THE ROWS BESIDE IT VERIFY, which is the only thing
# that qualifies a block to be here. It was read off the CI run of 2026-09-01
# that printed "instructions: every row is where it was" in the same job: an
# AMD Genoa, family 0x19 model 0x11 stepping 0x1.
#
# It is not the only such CPU, and cannot be. The pool held four in four runs
# that day — this Genoa, an AMD Milan (0x19/0x1), an Intel Ice Lake-SP
# (0x6/0x6a), against the Cascade Lake (0x6/0x55) of the container the check
# was written in — and the rows matched on more than one of them. Most CPUs
# select the same routines and count identically; the point of this file is the
# ones that do not.
#
# 18 of the 123 lines differ between this Genoa and that Milan, both AMD, one
# generation apart. Among them rep_movsb_stop_threshold, isa_1 and the whole
# cache geometry.
#
# Replace it only from a run that BOTH names its silicon and matches every row,
# and say in the pull request which host they moved to. While no block is
# recorded at all, CI prints one beside the rows so that a first one can exist.
#
# cpuid[0x1] is absent by design: its top byte is the initial APIC id, and it
# took three values in six runs on one host. Every other line held.
