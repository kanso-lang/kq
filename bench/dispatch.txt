# The CPU features glibc's ifunc resolvers read when they pick memcpy,
# memcmp, strlen and their neighbours, as ld.so reports them. Sorted, so
# a diff reads line by line.
#
# This exists because the vein beside it moved 0.06% to 0.10% on all four
# rows between two runs whose every printed version — rustc, LLVM, runner
# image, glibc, valgrind, gdb — agreed to the commit hash. The one thing
# that differed was the Azure region, which is to say the silicon.
#
# The mechanism is measured, not inferred. Same kq binary, same libc, one
# GLIBC_TUNABLES away, counted under callgrind on 2026-09-01:
#
#   default                       76,742,430   __memcpy_avx_unaligned_erms
#   -AVX2_Usable                  76,746,433   __memcpy_avx_unaligned_erms
#   -AVX_Fast_Unaligned_Load      76,488,416   __memcpy_sse2_unaligned_erms
#   -ERMS                         76,262,756   __memcpy_avx_unaligned
#
# A 0.63% spread from the dispatch alone, which is an order of magnitude
# more than most of what this vein exists to catch. Pinning the glibc
# revision does not pin any of it: the libc is identical in every row.
#
# Regenerate only when the rows are re-measured on the new host, and say
# in the PR which silicon they moved to.
#
# cpuid[0x1] is absent by design: its top byte is the initial APIC id and it
# changed three times in six runs on one host. Every other line held.
